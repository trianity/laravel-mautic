# 1.0.0 pre-release readiness audit

Audited commit: `71d0594348b87d9d90cc0e19329b4eb716be6d7f`
(`main`, 2026-10-23).

Audit date: 2026-10-24.

## Conclusion

The implemented runtime is a credible 1.0.0 candidate, and the current offline suite and
the exact-commit PHP/Laravel CI matrix are green. Two release-facing groups of corrections
are required before tagging:

1. OAuth installation must not direct users to the aggregate migration tag. The current
   command publishes every optional subsystem, not only OAuth storage.
2. The public README and exported archive must be made internally consistent. It contains
   stale development wording, omitted migration prerequisites, machine-local examples and
   links to files deliberately excluded from the archive.

No production-code rewrite, campaign configuration, Mautic plugin, Kaszanap integration,
or new load-test framework is required for 1.0.0. No release, tag or Packagist publication
was performed by this audit.

## Release inventory

### Supported public runtime surface

- Laravel auto-discovery registers `MauticServiceProvider`; `MauticManager`, named
  `MauticConnection` instances and the optional `Mautic` facade are the primary immediate
  API entry points.
- `MauticConnection` exposes normalized contact reads, discovery and writes, explicit
  email-restriction writes, static-segment operations and the raw SDK escape hatch.
- Durable entry points are `ContactOutbox`, `SubscriptionDelivery` and `WebhookInbox`.
  Their pollers, processors, jobs and operator services are part of the documented host
  integration boundary, but they do not make host business decisions.
- `OAuth2Service` owns authorization URL and callback completion without registering a
  route or issuing a redirect. Its stores, credential provider, token endpoint and refresh
  lock are replaceable contracts.
- Reconciliation exposes `ContactReconciler`, `MappingRecoveryService`, diagnostics and
  the commands `mautic:reconcile`, `mautic:reconcile-mappings` and `mautic:diagnose`.
- There are 22 explicit contracts under `src/Contracts`. Host-required extension points
  include `InboundContactProjector`; credential, transport, storage and clock contracts
  remain deliberate extension points rather than residue.
- `src/Fakes/FakeContactReader` and `FakeContactWriter` are intentional public host-test
  utilities. They have no Pest/Testbench dependency and belong in the runtime archive.

The package registers three queue jobs (`ProcessContactOutboxJob`,
`ProcessSubscriptionJob`, `ProcessWebhookInboxJob`) but no schedule. Hosts must run the
relevant queue and schedule the bounded outbox, subscription and inbox pollers plus any
desired reconciliation invocation. Provider boot publishes assets and registers commands;
it does not load or run migrations and does not register routes.

### Configuration

`config/mautic.php` has eight top-level areas: `default`, `oauth`, `identity`, `outbox`,
`subscription`, `inbox`, `reconciliation` and named `connections`. Every configured table
or database-connection key was traced to its migration and runtime store. Queue, lease,
attempt, delay, body-size, page-size, interval and reservation values are read by the
corresponding runtime service. No ignored configuration key was found.

### Dependencies and discovery

- Runtime: PHP `^8.4`, Guzzle `^7.9`, Illuminate contracts/database/encryption/support
  `^12 || ^13`, official `mautic/api-library ^4.0`, and PSR-18 `psr/http-client ^1.0`.
- Development only: Larastan, Pint, Testbench, Pest and PHPStan.
- Runtime PSR-4 maps only `Trianity\LaravelMautic\` to `src/`; the test namespace is
  confined to `autoload-dev`.
- Laravel auto-discovery names only `MauticServiceProvider`. No root repository override,
  path repository, absolute dependency path, branch alias or development SDK revision is
  present. A clean consumer resolved the official `mautic/api-library` 4.0.0 tag.
- The documented contingency-fork policy is sound: a reviewed fork override belongs to a
  consuming root repository and is not forced on package consumers.

### Test and acceptance infrastructure

The default `composer check` remains offline. Deterministic unit/feature tests use fake
HTTP, and the real process tests use disposable shared SQLite. MariaDB and live Mautic
suites have separate opt-ins. Worker scripts under `tests/Support` all have a current
caller or a documented manual harness entry point; no dead worker or fixture was found.
The ignored `tests/.env`, acceptance SQLite database, encryption key and evidence JSON are
not tracked.

## Findings

### A-01 — Required: OAuth documentation uses the all-subsystem migration tag

- Category: schema clarity and installation correctness.
- Evidence: `README.md:64-78` describes an OAuth storage migration but runs
  `vendor:publish --tag=mautic-migrations`. `MauticServiceProvider::boot()` at
  `src/MauticServiceProvider.php:320-347` attaches OAuth plus identity, outbox, inbox,
  reconciliation and subscription stubs to that tag. The disposable schema check proved
  that this produces 19 tables, not the three OAuth tables described by the section.
- Impact: a host following the smallest OAuth setup is instructed to publish and migrate
  five unrelated optional subsystems. This violates the documented opt-in boundary and
  obscures ownership of the final schema.
- Smallest correction: add `mautic-oauth-migrations` for the OAuth stub, use that tag in
  the OAuth README section, and describe `mautic-migrations` explicitly as the aggregate
  convenience tag. Retain the aggregate tag for hosts intentionally installing everything.
- Change type: publication mapping plus documentation; do not rewrite the migration.
- Verification: assert one path under every subsystem tag, six unique destinations under
  the aggregate tag, and repeat empty-schema/custom-name/rollback verification.

### A-02 — Required: migration prerequisites are not presented as one coherent install map

- Category: schema ownership and public documentation.
- Evidence: the outbox processor depends on `ContactMappingRepository`, while
  `README.md:239-247` only publishes the outbox migration. Webhook processing also resolves
  mappings, while `README.md:430-439` only publishes inbox storage. Reconciliation compares
  remote contacts to mappings and applies mapping repair, while `README.md:530-539` only
  publishes reconciliation storage. Subscription explicitly requires the identity and
  outbox database connections to match (`config/mautic.php:38-49` and provider validation),
  but `README.md:325-334` does not tell a new consumer to publish those prerequisite
  schemas.
- Impact: the migration stubs are individually valid, but a new user can install a feature
  schema without the schema needed by its documented runtime path and meet a missing-table
  failure only in a worker.
- Smallest correction: add the canonical publication/dependency table below to the README
  and link each feature section to it. Keep every optional subsystem separate.
- Change type: documentation correction; no schema consolidation.
- Verification: add or retain feature-level fresh-schema tests that install precisely the
  documented prerequisite tags and resolve/process the relevant public service.

### A-03 — Required: the release-facing README is stale and has broken archive links

- Category: truthful documentation and distribution.
- Evidence:
  - `README.md:8-13`, `README.md:39-49` and `CHANGELOG.md:3` still describe an unreleased
    development-only install rather than the intended tagged 1.0.0 path.
  - `README.md:236` says Task 05 still owns delivery although delivery is implemented;
    `README.md:1004` calls the implemented identity “planned”.
  - `README.md:37` links `CONTRIBUTING.md`, and `README.md:1009-1013` links `AGENTS.md` and
    `.ai` handoff files. `.gitattributes:2-7` deliberately excludes all of those from the
    git archive. The audited archive therefore contains broken links.
  - `README.md:605-780` gives source-only live-test commands, while tests are excluded from
    the distribution. This history is useful in the repository but needs a clear source
    checkout boundary or a shorter link to retained compatibility reports.
  - `README.md:666` publishes a machine-specific `/home/holbok/...` example.
- Impact: consumers cannot follow one coherent Packagist installation path and may confuse
  development evidence or unavailable test tooling with installed runtime functionality.
- Smallest correction: make the top-level path `composer require
  trianity/laravel-mautic:^1.0`, retain a clearly labelled source-development section,
  replace/remove archive-broken links, use generic absolute paths, update implemented
  wording, and summarize live evidence with links to compatibility reports. Prepare the
  1.0.0 changelog/release notes at tagging time without claiming publication early.
- Change type: documentation correction.
- Verification: extract `git archive`, check every relative README link, and execute the
  install/config/publish examples in a disposable host.

### B-01 — Useful: remove test-only and bulky provenance material from the install archive

- Category: distribution hygiene.
- Evidence: `git archive HEAD` contains 260 entries and is 3,993,600 bytes. Tests are
  excluded, but `phpunit.live.xml`, `phpunit.oauth-live.xml` and
  `phpunit.oauth-fixture.xml` remain; their referenced test directories are absent. The
  3,218,593-byte `docs/reference/mautic/7.2.1/api-v2/openapi.json` is 81% of the archive and
  is not used by runtime code or the installation path.
- Impact: the three XML files are unusable in the installed package, and the raw API
  snapshot dominates every consumer download without providing runtime behavior.
- Smallest correction: add the three acceptance PHPUnit files and the raw OpenAPI snapshot
  to `export-ignore`. Keep the snapshot tracked in the repository and keep the concise
  provenance/capability and compatibility reports available on GitHub. `.editorconfig`,
  `.gitignore` and `.gitattributes` may also be excluded, but that is cosmetic.
- Change type: distribution exclusion, not deletion of historical evidence.
- Verification: inspect a new git archive and confirm runtime source, config, all six
  stubs, license, README, security guidance and the selected user documentation remain.

### B-02 — Useful: declare the directly used JSON extension explicitly

- Category: Composer metadata maintainability.
- Evidence: `composer.json:14-22` has no `ext-json` requirement, while runtime code calls
  `json_encode`, `json_decode` and uses `JSON_THROW_ON_ERROR` in the OAuth, outbox, inbox,
  subscription and console paths. Installation currently succeeds because both Guzzle and
  `mautic/api-library` require `ext-json`, so this is not a present resolver failure.
- Impact: the package's own platform requirement is implicit and would silently depend on
  unrelated future dependency metadata.
- Smallest correction: add `"ext-json": "*"` to `require`. Do not add optional/core
  extensions without direct evidence.
- Change type: Composer metadata.
- Verification: `composer validate --strict`, clean `--no-dev` consumer resolution and CI.

### B-03 — Useful: retire contradictory agent handoff history after the audit

- Category: development residue.
- Evidence: `.ai/STATE.md:42-44` says completed live-Mautic compatibility acceptance is not
  implemented, while the same file records successful scoped Mautic 7.2.1 probes beginning
  at `.ai/STATE.md:57`. `.ai/prompts/08-release-readiness.md:4-7` directs a future agent to
  implement with TDD and modify README/STATE, whereas the selected readiness task is an
  audit-only milestone. `.ai/STATE.md` is also mostly chronological implementation history
  rather than a compact current handoff.
- Impact: future maintenance can resurrect superseded task behavior or misstate the exact,
  capability-scoped compatibility evidence.
- Smallest correction: replace Prompt 08 with the approved follow-up cleanup scope, make
  the current-state summary distinguish scoped Mautic 7.2.1 evidence from a blanket support
  claim, and archive rather than erase useful dated evidence.
- Change type: development documentation only.
- Verification: compare the revised state against the retained compatibility reports and
  confirm it does not broaden compatibility claims.

No category C item is necessary for release readiness. Deferred consent ownership,
conditional restriction release, campaigns, mail delivery and host integration remain
features, not cleanup findings or 1.0.0 blockers.

## Canonical migration and publication map

| Order | Dedicated tag | Tables | Active owner and important state | Runtime dependency |
| --- | --- | --- | --- | --- |
| 00 | proposed `mautic-oauth-migrations` | `mautic_oauth_tokens`, `mautic_oauth_states`, `mautic_oauth_locks` | encrypted token payload, expiry/generation CAS, context-bound state, connection lock owner/expiry | only OAuth connections |
| 01 | `mautic-identity-migrations` | `mautic_contact_mappings` | byte-exact connection/local/remote hashes, remote state, merge target and generation | outbox processing, inbound processing, reconciliation; subscription |
| 02 | `mautic-outbox-migrations` | commands, aggregate locks, operator audits, connection blocks | immutable payload/revision, delivery phase, retry/lease, remote evidence and OAuth blockers | identity; subscription |
| 03 | `mautic-inbox-migrations` | deliveries, events, contact locks | receipt/body identity, encrypted payload, semantic identity, status/lease/order | identity and host `InboundContactProjector` for processing |
| 04 | `mautic-reconciliation-migrations` | checkpoints, observations, findings, audits | high-water cursor, request reservation, ID-only evidence and operator repair audit | identity for comparisons and default atomic repair |
| 05 | `mautic-subscription-migrations` | intents, segment associations, segment locks, audits | stable event semantics, prerequisite IDs, membership phases/retries, provisioning blocker and operator audit | identity and outbox on the same configured database |

`mautic-migrations` should remain the documented aggregate of all six stubs. The date and
sequence are coherent, every table is created exactly once, and there are no historical
upgrade migrations, empty bridges, repeated corrections or obsolete tables in the current
repository. The separate subsystem stubs are the right final installation model; combining
them would weaken optional ownership boundaries.

The disposable SQLite audit created all 19 tables using custom table names and one custom
database connection, then ran all six `down()` methods in reverse order and left zero
tables. Runtime queries were traced for every table and important identity, status,
generation, lease, retry, evidence and audit field. No unused persisted state was found.

## Production-code residue assessment

A symbol/caller scan over all 190 runtime PHP files found no unreferenced runtime class,
superseded implementation, abandoned feature flag or obsolete exception/outcome candidate
that is safe to remove. Apparently internal DTOs, enums and exceptions are reached through
serialization, SDK boundaries, stores or public return/throw contracts. The database
generation/owner/expiry checks, ambiguity outcomes, connection blocks, segment-key blockers
and membership phase state all protect documented concurrency or recovery behavior and
must remain.

The service provider's many bindings reflect separate opt-in subsystems. Collapsing them or
introducing a generic workflow engine would be redesign, not release cleanup. Likewise the
stock restriction writer, raw SDK access and public fakes are deliberate API choices.

## Proposed distribution

Keep in the 1.0.0 install artifact:

- `composer.json`, `LICENSE.md`, `README.md`, `CHANGELOG.md`, `SECURITY.md`;
- all runtime `src/` files, `config/mautic.php`, and all six migration stubs;
- host migration guidance, architecture/decision documents needed to explain safety
  contracts, and concise compatibility reports supporting scoped claims.

Exclude from the install artifact while retaining in the repository:

- tests, worker harnesses, test databases/evidence, PHPUnit/Pest/Testbench/PHPStan/Pint
  configuration and CI/agent/task material;
- the raw generated OpenAPI JSON (retain its provenance and capability summary in the
  repository);
- local IDE, cache, build and dependency directories.

The tracked-file scan found no credentials, tokens, private keys, real contact fixtures,
database files, logs, caches or generated acceptance evidence. The only tracked
machine-specific path is the documentation example identified in A-03. A local
`composer archive` from the dirty development directory included ignored local caches,
tools and `vendor`; that output is not an acceptable release artifact. The clean
`git archive` result above is the relevant audited source boundary.
