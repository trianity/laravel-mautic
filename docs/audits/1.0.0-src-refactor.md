# 1.0.0 production-source refactor review

Audited commit: `99d74bb95713b9db08c9605be588d15bf603e1a9`
(`main`, 2026-10-24).

Review date: 2026-10-24.

## Conclusion

The production source is suitable for the 1.0.0 release without a structural rewrite.
The review found two bounded readability improvements that can be completed before the
release with acceptable risk, provided they are implemented separately and preserve the
existing construction and persistence contracts:

1. Organize `MauticServiceProvider::register()` into private, subsystem-specific
   registration methods without changing registration order or container semantics.
2. Extract the stored subscription-row hydration in
   `DatabaseSubscriptionStore::get()` into one private mapper after first adding a
   corruption characterization test.

Larger extractions around OAuth configuration, processors and database stores are valid
future maintenance ideas, but are not justified immediately before 1.0.0. The apparent
duplication between outbox, inbox, reconciliation and subscription state machines is
mostly semantic rather than incidental and should remain explicit.

No correctness defect was identified. This was a static refactor review backed by the
existing offline suite; it is not new independent proof of database or remote-system
concurrency behavior.

## Scope and method

All 190 production PHP files under `src/` were inventoried and reviewed by subsystem.
The review traced relevant public documentation, `config/mautic.php`, the six canonical
migration stubs, provider bindings, architecture decisions, the prior readiness audit,
and the unit, feature and process-level tests protecting the selected boundaries.

The largest and most stateful files received additional method- and transition-level
inspection: `DatabaseSubscriptionStore` (656 lines), `DatabaseOutboxStore` (611),
`MauticServiceProvider` (479), `SubscriptionProcessor` (418),
`DatabaseReconciliationStore` (385), `SdkContactWriter` (309),
`DatabaseWebhookInboxStore` (303), `OutboxProcessor` (283),
`SdkResponseBoundary` (259), `ContactResponseMapper` (253), and
`DatabaseContactMappingRepository` (251).

This review did not modify production code, tests, configuration, migrations or public
APIs. It did not run live Mautic or opt-in MariaDB suites.

## Behavioral baseline to preserve

A future refactor must treat the following as behavior, even where PHP visibility alone
would permit a change.

### Public and Laravel contracts

- Runtime PSR-4 exposes every class under `Trianity\LaravelMautic`; constructors, public
  methods, the 22 interfaces under `src/Contracts`, DTO shapes, enum backing values and
  documented exception types are consumer-visible contracts.
- Laravel auto-discovery must continue to register only `MauticServiceProvider`. Provider
  construction and boot must remain lazy: resolving the manager, facade or publications
  must not establish a database or network connection.
- `bindIf` and `singletonIf` extension points must continue to respect host bindings.
  Concrete singleton lifetimes, named connection caching and `MauticManager::purge()`
  behavior must remain unchanged.
- Provider boot must continue to publish exactly one canonical migration under each
  subsystem tag and the same six ordered paths under `mautic-migrations`; it must register
  the same three commands and no route or implicit migration.
- `FakeContactReader` and `FakeContactWriter` are public runtime testing utilities, not
  removable test residue.

### Configuration, data and storage contracts

- All keys and defaults in `config/mautic.php`, including timeout, lease, attempt, delay,
  queue, page-size, reservation, database-connection and table-name settings, must remain
  stable.
- Connection URL canonicalization, Basic/OAuth selection, HTTPS rules, finite positive
  timeouts and the rule that `connect_timeout` cannot exceed `timeout` must not change.
- The six migration schemas, table/column names, indexes, encrypted fields and configured
  database boundaries are fixed for the first release candidate.
- Stored JSON representations, enum strings, sanitized reason codes, operation IDs,
  semantic hashes, byte-exact identity hashes, segment definition hashes and revision
  ordering must remain byte-compatible.
- `OptionalValue` and related mapping code must retain all three states: a missing member,
  an explicit `null`, and a present value. Integer/string normalization must not become
  more permissive as a side effect of cleanup.

### Remote and failure contracts

- Exact HTTP methods, endpoints, payloads, request order and maximum request counts are
  observable. In particular, validation and safe preflight reads precede mutation, a
  post-mutation fallback read occurs at most once, and a side-effectful mutation is never
  automatically replayed when completion is ambiguous.
- Read, write, OAuth, not-found, malformed-response, throttling and ambiguous-outcome
  exception classifications must remain distinct. Remote bodies and credentials must not
  enter stored or displayed diagnostics.
- Numeric `Retry-After` remains a server-directed minimum; malformed values remain
  ignored. Local exponential backoff, jitter, caps and maximum-attempt comparisons must
  preserve their current formulas and attempt numbering.
- Transactions, after-commit dispatch, lost-dispatch polling and rollback behavior must
  retain their current boundaries.
- Every owner, generation, expiry, revision and expected-state predicate on conditional
  database updates is safety-critical. A refactor must continue to reject stale workers
  and retain remote evidence when local completion becomes uncertain.
- Ambiguous create, update, provisioning and membership outcomes must remain blocked until
  the existing operation-specific read proof or explicit operator attestation is supplied.
  Audit writes and the state transition they authorize must remain atomic.

## Subsystem findings

### Manager, connection and service provider

`MauticManager` and `MauticConnection` are small composition surfaces with clear named
connection caching and normalized capability access. No change is recommended there.

`MauticServiceProvider::register()` (`src/MauticServiceProvider.php:74-312`) is a single
238-line registration block spanning every subsystem. Its registrations are coherent but
navigation is costly, and changes to one subsystem require reviewing unrelated bindings.
The private configuration readers at lines 358-436 also repeat the same non-empty-string
normalization. Candidate A-01 proposes only structural private-method extraction. A
generic registration DSL, loop-driven binding table or new provider classes would obscure
ordering and Laravel container semantics and is not recommended.

`boot()` (`src/MauticServiceProvider.php:314-355`) is repetitive but explicitly shows the
six publication mappings and their dedicated and aggregate tags. Existing tests assert
these paths exactly. It should remain explicit during A-01; a publication abstraction is
too little benefit for another moving part immediately before release.

### Configuration and authentication factories

`ConnectionConfig`, `GuzzleHttpClientFactory`, `ApiLibraryAuthenticationFactory` and
`ApiLibraryConnectionFactory` each have one clear boundary. Their duplication is limited
to deliberately separate validation and construction concerns.

OAuth connection values are decoded in several forms by
`ConnectionConfig::fromArray()` (`src/Configuration/ConnectionConfig.php:23-97`),
`OAuth2Service::settings()` (`src/OAuth/OAuth2Service.php:92-125`),
`HttpOAuthTokenEndpoint::connection()` (`src/OAuth/HttpOAuthTokenEndpoint.php:144-152`)
and `EnvironmentOAuthClientCredentialsProvider::forConnection()`
(`src/OAuth/EnvironmentOAuthClientCredentialsProvider.php:16-29`). A typed internal
settings object could reduce repeated raw configuration access, but doing it properly
would alter sensitive constructor and validation boundaries. Candidate B-01 defers it.

### SDK response boundaries, metadata and contact/segment mapping

`SdkResponseBoundary` is long because it deliberately maps read and mutation errors into
different public exception families and promotes transport uncertainty only for operations
whose safety metadata requires it (`src/Support/SdkResponseBoundary.php:27-233`). The
parallel read/write paths are not safely interchangeable. `SdkResponseMetadata` remains a
small adapter around SDK response metadata.

`ContactResponseMapper` is branch-heavy because it preserves malformed, missing, null and
value states rather than collapsing them. Splitting its individual field parsers into new
classes would add indirection without reducing policy. `SdkStaticSegmentGateway` similarly
keeps exact alias, publication and filter checks near the SDK response. No pre-release
refactor is recommended.

### Contact reads, writes, discovery and restriction commands

The reader, discovery and writer implementations separate orchestration from response
mapping sufficiently. Their exact preflight, POST/PATCH, batch-index and response-metadata
paths are extensively characterized by `NormalizedContactReadsTest`,
`NormalizedContactWritesTest` and `StaticSegmentOperationsTest`.

`SdkContactRestrictionWriter::verifiedState()`
(`src/Support/SdkContactRestrictionWriter.php:109-155`) intentionally attempts embedded
state parsing and then one GET fallback. The broad catch around the fallback is a privacy
and public-error boundary: it returns a sanitized `RestrictionStateNotVerified` instead
of leaking SDK or response detail. It must not be extracted into a generic retry helper or
changed to replay a mutation. No pre-release refactor is recommended.

### Contact identity and field ownership

`DatabaseContactMappingRepository` centralizes mapping hydration and expected-generation
queries already. Its repeated connection and remote-ID validation express distinct public
preconditions. `ContactIdentityHasher` makes the different tuple domains explicit.

`FieldMapper`, `HostContactFields`, `FieldRule` and `FieldChange` clearly encode allowlists,
ownership and missing/null/value intent. A more generic mapping framework would weaken
these visible policies. No worthwhile pre-release change was found.

### OAuth authorization, tokens, refresh and persistence

OAuth authorization, callback state, endpoint exchange, encrypted versioned storage and
refresh locking are separated by replaceable contracts. The similar persistence handling
in `OAuth2Service::complete()` and `OAuthTokenManager` is not equivalent: refresh must
re-read under the lock and can converge on a newer token from another worker. It should
not be deduplicated.

The database repositories keep generation comparison, encryption and lock ownership close
to their SQL. Existing feature and real multi-process tests cover state consumption and
refresh locking. Apart from deferred candidate B-01, no refactor is recommended.

### Contact outbox

`DatabaseOutboxStore` and `OutboxProcessor` are large, but their explicit methods expose a
reviewable durable protocol: aggregate ordering, lease ownership, remote evidence,
connection blockers and atomic operator audits. The processor's retry calculation at
`src/Outbox/OutboxProcessor.php:216-254` resembles subscription backoff, but its retryable
failure set, create/update ambiguity rules and attempt state differ. A shared policy helper
would need modes and callbacks and is rejected under C-01.

Splitting the store into multiple repositories would make transaction ownership and
conditional-update invariants cross-object concerns. Candidate B-02 records that possible
long-term decomposition but defers it until a concrete maintenance change supplies a
better boundary.

### Webhook inbox and projection

Webhook ingress keeps authentication and payload limits before persistence; the database
store atomically records deliveries and events, then independently coordinates event and
contact leases. The processor keeps ordering, semantic deduplication, field ownership and
mapping transitions explicit. These concerns look similar to outbox claims but have
different identities and terminal rules. Existing tests cover rejection-before-write,
encryption, recovery, stale ordering and contact leases. No refactor is recommended.

### Reconciliation, diagnostics and mapping recovery

`ContactReconciler` coordinates one bounded reserved request at a time, while
`DatabaseReconciliationStore` owns checkpoints, observations, findings and exact stale
reservation rejection. This explicit division is appropriate. `DatabaseMauticDiagnostics`
uses repetitive count queries, but each names a separate configured store and the result
is privacy-bounded; a generic diagnostics registry would add policy machinery.

Mapping recovery deliberately separates dry-run selection from atomic, audited apply.
Commands remain thin adapters. The process-level reconciliation test is the relevant
concurrency proof and must not be replaced with an in-memory fake. No pre-release refactor
is recommended.

### Subscription capture, provisioning, membership and operator recovery

`DatabaseSubscriptionStore::get()` (`src/Subscription/DatabaseSubscriptionStore.php:61-88`)
mixes lookup, JSON validation and a 22-field record construction. Unlike the store's other
transition methods, this is a pure row boundary that can be named and isolated without
changing the state machine. Candidate A-02 recommends a private mapper with exact casts
and constructor order retained.

`SubscriptionProcessor::process()` (`src/Subscription/SubscriptionProcessor.php:40-232`)
and `resolveSegment()` (lines 316-383) are long, but their ordering is the protocol:
contact completion, active mapping, segment-key claim, create marker, retained evidence,
membership preflight, mutation and verification. Breaking those phases into collaborating
services before release would make the durable handoffs harder to audit. Candidate B-03
defers any phase-object redesign.

The near-identical suitability and definition-hash code in `SubscriptionProcessor`
(lines 385-417) and `SubscriptionOperator` (lines 137-153) is intentional. The processor
persists stable machine reason codes while the operator raises human-facing recovery
errors. Sharing it would require a presentation mode or would change observable evidence;
the five-line hash alone does not justify coupling them.

### Console commands, jobs, DTOs, enums and public fakes

The three console commands and three queue jobs are thin framework adapters. DTOs and enums
make persisted and returned states explicit; no getter-only abstraction or test is needed.
The public fakes implement consumer-facing contracts without development dependencies and
have focused deterministic tests. No worthwhile refactor was identified.

### A-01 — Organize provider registration by subsystem

- Priority: high among refactors; not a release blocker.
- Exact location: `src/MauticServiceProvider.php:74-312`, especially the OAuth, identity,
  outbox, subscription, inbox, reconciliation and manager registration groups.
- Problem: one method contains unrelated subsystem construction and validation details,
  making a local binding change expensive to review.
- Smallest transformation: keep `mergeConfigFrom()` first, then call private methods such
  as `registerCore()`, `registerOAuth()`, `registerOutbox()`,
  `registerSubscription()`, `registerInbox()`, `registerReconciliation()` and
  `registerManager()` in the current order. Move existing statements byte-for-byte where
  practical. Do not introduce new provider classes, loops, descriptor arrays or generic
  binding helpers. Leave `boot()` and configuration normalization unchanged in this step.
- Expected benefit: each subsystem's dependency graph becomes visible in one bounded
  method, and future changes no longer require navigating a 238-line block.
- Public/persisted contracts: none may change; container bindings and construction are
  public integration behavior.
- Invariants: identical registration order, binding type (`bindIf`, `singletonIf` or
  `singleton`), closure laziness, singleton lifetime, configuration reads, validation
  timing, command/publication behavior, and absence of routes/network/database work.
- Risk: low-medium because the edit is mechanical, but a changed binding primitive or
  eager resolution would affect host applications.
- Existing protection: `tests/Feature/ManagerTest.php` covers lazy resolution, named
  connection caching and exact publications; subsystem feature tests resolve the concrete
  services; `tests/Integration/MauticServiceProviderRouteTest.php` proves the provider adds
  no route.
- Missing characterization: before moving code, add one provider-focused test that
  pre-binds representative replaceable contracts before provider registration and proves
  the `bindIf`/`singletonIf` defaults do not replace them. This observes an intentional
  extension contract rather than private method structure.

### A-02 — Isolate subscription record hydration

- Priority: medium; optional if release timing is tight.
- Exact location: `DatabaseSubscriptionStore::get()` at
  `src/Subscription/DatabaseSubscriptionStore.php:61-88`.
- Problem: query/no-row control flow is mixed with JSON decoding, payload-shape validation,
  enum reconstruction, nullable casts and a long constructor call.
- Smallest transformation: retain the query and null return in `get()`, then pass the row
  to a private `map(object $row): SubscriptionRecord`. Move the current decode, array
  checks and constructor unchanged. Do not create a generic hydrator or alter the DTO.
- Expected benefit: the stored-row compatibility boundary is named and can be reviewed
  separately from retrieval.
- Public/persisted contracts: `get()` return/exception behavior and every stored cast.
- Invariants: `JSON_THROW_ON_ERROR`, the explicit non-array error, enum `from()` failures,
  nullable integer/string handling and exact constructor argument order.
- Risk: low; the transformation is local but persisted data makes silent coercion changes
  consequential.
- Existing protection: `tests/Feature/SubscriptionDeliveryTest.php` and the SQLite process
  suites repeatedly hydrate records across every durable phase.
- Missing characterization: add one database-level test that places a valid JSON scalar in
  either stored payload column and asserts the existing `RuntimeException` instead of a
  partially hydrated record. Existing process tests cover valid rows but do not explicitly
  pin this corruption boundary.

### B-01 — Typed OAuth settings boundary

- Exact locations: `ConnectionConfig::fromArray()` at
  `src/Configuration/ConnectionConfig.php:23-97`, `OAuth2Service::settings()` at
  `src/OAuth/OAuth2Service.php:92-125`, `HttpOAuthTokenEndpoint::connection()` at
  `src/OAuth/HttpOAuthTokenEndpoint.php:144-152`, and
  `EnvironmentOAuthClientCredentialsProvider::forConnection()` at
  `src/OAuth/EnvironmentOAuthClientCredentialsProvider.php:16-29`.
- Smallest credible transformation: introduce one internal typed settings resolver while
  keeping secrets outside Laravel configuration and preserving all public constructors or
  offering a compatibility path.
- Benefit: one validation vocabulary and fewer raw array reads.
- Risk/timing: medium-high and deferred; it touches authorization URL generation, callback
  exchange, refresh, DI and sensitive data. Existing `ConnectionConfigTest`,
  `OAuthLifecycleTest` and `OAuthCorrectionsTest` are strong, but a constructor-compatible
  design decision should precede implementation.

### B-02 — Persistence store decomposition

- Exact locations: `src/Outbox/DatabaseOutboxStore.php` and
  `src/Subscription/DatabaseSubscriptionStore.php`.
- Smallest credible transformation: only after a concrete change identifies a stable
  boundary, extract a transaction-complete responsibility such as read-only diagnostics;
  do not split individual transitions from their expected-state predicates.
- Benefit: potentially smaller units for future evolution.
- Risk/timing: high and deferred. Current stores are large because they own cohesive SQL
  state machines. Existing feature, fault-injection and process tests protect behavior,
  but no current maintenance need outweighs the new cross-object transaction reasoning.

### B-03 — Subscription phase collaborators

- Exact locations: `SubscriptionProcessor::process()` and `resolveSegment()` at
  `src/Subscription/SubscriptionProcessor.php:40-232,316-383`.
- Smallest credible transformation: first document a phase input/output contract and then
  consider extracting only a complete remote phase with no transaction ownership.
- Benefit: potentially shorter orchestration and more local remote-failure mapping.
- Risk/timing: high and deferred. Exact create markers, lease assertions, evidence writes
  and no-replay decisions span the apparent boundaries. The extensive subscription
  feature and real multi-process SQLite tests must remain the safety net.

## Intentional complexity to preserve

### C-01 — Independent durable state machines

Outbox aggregate claims, webhook event/contact leases, reconciliation reservations and
subscription intent/segment claims share SQL vocabulary but not identity, expiry, recovery
or terminal semantics. A generic claim repository would require callbacks, mode flags and
configurable transition policy. Keep the implementations independent and explicit.

### C-02 — Operation-specific retry and ambiguity handling

Outbox creates, updates, membership preflight, membership mutation, segment creation and
post-write verification have different replay safety. Similar backoff arithmetic does not
make their classification or state transitions equivalent. Keep the rules adjacent to the
owning processor.

### C-03 — Response parsing distinctions

Read and write normalization, embedded mutation responses, one-read fallback verification,
contact optional values and segment definitions deliberately accept different shapes and
throw different exceptions. Do not replace them with a permissive generic response mapper.

### C-04 — Explicit conditional SQL and evidence retention

Owner/generation/expiry predicates, affected-row checks, create-in-flight markers, remote
IDs and operator audits are verbose because they prevent stale completion and blind replay.
Do not compact them into implicit active-record updates or distribute one transition across
repositories.

### C-05 — Processor/operator validation duplication

Subscription processing persists stable error codes; operator recovery presents actionable
exceptions and writes an audit. Their similar suitability checks have different output
contracts and should not be joined by a mode-bearing helper.

## Correctness defects

None identified. In particular, the broad exception conversion in restriction fallback
verification and the repeated claim implementations were reviewed as possible concerns;
their sanitized public errors and operation-specific state semantics are intentional.

If implementation of either A candidate exposes a behavior discrepancy, it must be
reported and fixed as a separate correctness change rather than hidden inside the
refactor.

## Recommended pre-release selection

Implement A-01 first as one isolated commit. It has the clearest maintenance benefit and
does not require changing a public or persisted shape. Implement A-02 only as a second
commit if the corruption characterization test is added first and the release schedule
allows another full check. Neither item is required to call the present code a credible
1.0.0 candidate.

Do not combine either change with B candidates, config-helper deduplication, publication
rewrites, naming changes or formatting churn.

## Ordered implementation and verification plan

1. **Characterize host extension preservation.** Add a focused provider test that
   registers host implementations before the package provider and proves representative
   `bindIf` and `singletonIf` contracts remain selected. Run
   `./vendor/bin/pest tests/Feature/ManagerTest.php tests/Integration/MauticServiceProviderRouteTest.php`.
   Broaden only if the new test reveals a current discrepancy.
2. **Extract provider registration methods.** Move the current statements into private
   subsystem methods in the same order. Run the two provider-focused files, then the
   feature files for every moved subsystem. A reviewer should compare the before/after
   binding sequence and primitives, confirm closures still resolve lazily, and inspect
   `MauticServiceProvider::pathsToPublish()` for unchanged mappings.
3. **Verify A-01 globally.** Run `composer check` and `git diff --check`. If any lifecycle,
   binding or static-analysis failure appears, keep the change bounded and revert the
   extraction rather than weakening assertions.
4. **Characterize corrupt subscription payloads.** In a separate change, insert a stored
   scalar payload and pin the current `RuntimeException`. Run
   `./vendor/bin/pest tests/Feature/SubscriptionDeliveryTest.php`.
5. **Extract the subscription mapper.** Move only existing hydration logic to a private
   method. Re-run `SubscriptionDeliveryTest`, then the two subscription process suites if
   available in the default environment. A reviewer should compare every cast, enum
   conversion and constructor position and confirm the query and null behavior are
   unchanged.
6. **Verify A-02 globally.** Run `composer check` and `git diff --check`. Opt-in MariaDB or
   live Mautic checks are justified only if implementation changes SQL, transactions,
   configuration or remote orchestration; the proposed mapper extraction must not do so.

Each coherent refactor should keep source and tests green before the next begins. Any need
to change a public signature, stored representation, query predicate, HTTP sequence or
exception contract is a stop condition requiring a separate design decision.

  passed; Pest passed 319 tests / 1552 assertions with seven explicitly opt-in tests
